## What the drift removal does, and its effect on images without the drift (added 2026-10-16)

`check_real_images.column_trend`: per row, subtract the overscan median (as WADERs does); keep the pixels within ±0.6 ADU
of zero (zero-electron pixels; charge is left out); per column, the median of those pixels over all rows; a running median
over 25 columns; zero in the overscan; subtract this one curve from every row. It removes only baseline structure that is
smooth along the row and the same in every row; single-column features, row-to-row offsets and charge are untouched.

On images WITHOUT the drift:
* 6 simulated 16-row images (known truth): it removes 0.02–0.04 ADU rms (the noise of the estimate; 0.05–0.07 on the
  noisy channel); labels against the truth unchanged within the scatter (σe +1.6 → +1.5 %, λ +4.1 → +4.4 % median,
  RMS 10.0 → 8.6 %, gain 0.0 → +0.2 %; χ²/ndf 0.92 → 0.96).
* real 10-06 image: 0.02–0.07 ADU rms; up to 0.5 ADU only in the first 2–3 columns (edge: the odd first pixels and few
  zero-electron pixels there).
Weak points, to fix before using it in processing: the fixed ±0.6 ADU window (should scale with the measured noise; it
clips the zero peak of a noisy channel), the first columns (exclude or require a minimum number of zero-electron pixels),
and it needs enough zero-electron pixels per column (fine at λ ≲ 1 e-/pixel).

**Correction.** The earlier statements "the 10-06 image has no drift" and "10-06 used FILTER 85" were wrong. The FILTER 85

EXPOSURE 10, NDCMPRE 0, BOOLCLR 1, NCOLPRE 5300; 5800 for the 100-row images). Measurable only where the zero-electron peak
is resolved (overscan noise ≲ 0.6 ADU): board 101 at 100, 500, 1000, 2000 and 5000 skips (ch0; ch3 at 100 and 500).

* **It has been there since at least 2026-10-14**, at every skip count where it can be measured, on ch0, ch1 and ch3.
* **It recovers over a similar number of COLUMNS (~300–800) whatever the skip count**, i.e. over very different TIMES
  (~1 s at 100 skips, ~25 s at 1000): it follows the pixels read since the row started, not a time constant.
* **Same in the first and last rows** of a 250-row image (rows 0–49 vs 200–249): it happens at the start of every row,
  not with exposure.
* **Board 102's channels without a CCD (EXT1, EXT4) show none** (|offset| ≤ 0.05 ADU), with the same sequencer, prescan
  skip, register clear and readout: not a generic electronics or clocking effect; it needs board 101 with the PA03 CCD
  (its output stage, or something on board 101's chain). Board 102's CCD channel (EXT3) is too noisy to tell.
* The 5000-skip image (readout starting 500 columns later, NCOLPRE 5800) shows its dip at its OWN first columns (−0.2),
  more than the 5300-images show at the same physical column (~−0.08): weak evidence that it follows the start of the
  readout, not a place on the CCD.

**Tests that would localize it (1–2 images each, 16 rows, 500 skips, NDCMPRE 5):**
1. `BOOLCLR = 0` (no serial-register clear before each row): does the clear cause it?
2. `NCOLPRE = 5000` (start reading 300 columns earlier): does the dip move with the start of the readout (row-start
   effect) or stay at physical column ~5300 (CCD structure)?
3. A board-101 channel with the CCD's output disconnected is not possible, but swapping which board reads the module would
   separate board 101's chain from the PA03 output stage (only if practical).
Until then, the software trend removal is the fix: tested harmless on images without the drift.

## Is the software correction physical? (added 2026-10-16, after the user's concern)

**Test 1 — what the drift does to the electron comb** (5 images, board 101; two Gaussians fitted per column block):

| ch0 block | 0e- position (ADU, rel. to overscan) | gain = 1e- − 0e- (ADU/e-) | 0e- width (ADU) |
|---|---|---|---|
| 0–25 | −0.912 | 1.25 ± 0.12 | 0.279 |
| 25–50 | −0.701 | 1.26 ± 0.09 | 0.242 |
| 50–100 | −0.572 | 1.35 ± 0.04 | 0.238 |
| 100–200 | −0.403 | 1.35 ± 0.04 | 0.231 |
| 200–400 | −0.242 | 1.344 ± 0.011 | 0.220 |
| 400–852 | −0.100 | 1.340 ± 0.007 | 0.212 |

(ch1 and ch3 the same: shift −0.92/−0.99 at the start, −0.11/−0.15 at the end; gain constant within errors.)
* **The gain does not change along the row**: the whole comb shifts. The drift is a baseline (pedestal) shift, not a change
  of charge or gain, so subtracting it is the same kind of step as the per-row pedestal subtraction itself.
* **But the earlier correction was incomplete**: the shift at the row start is −0.9 to −1.0 ADU (~0.7 e-), not −0.45 (its
  ±0.6 ADU window clipped the shifted peak); and even at the end of the row the active level is 0.1–0.15 ADU below the
  overscan.
* **The noise is higher at the row start** (+30 % in the first 25 columns, +12 % to column 100, +4 % to 400): an offset
  correction cannot remove that.

**Test 2 — cut the start of the row instead** (columns 0–199 removed; NCOLPRE/NCOL in the header adjusted so run_WADERs'
geometry stays right):

| variant | σe ch0 / ch1 / ch3 (repeat scatter) | χ²/ndf |
|---|---|---|
| full rows, as recorded | 0.190 / 0.195 / 0.234 (2.9 / 4.1 / 3.0 %) | 2.7–5.1 |
| full rows, trend removed | 0.164 / 0.170 / 0.213 (3.0 / 1.5 / 1.2 %) | 1.2–3.5 |
| **first 200 columns cut, nothing subtracted** | **0.163 / 0.167 / 0.206 (1.6 / 2.6 / 1.0 %)** | **0.8–1.3** |
| cut + trend removed | 0.156 / 0.161 / 0.200 (2.1 / 1.3 / 0.9 %) | 0.8–1.2 |

* Cutting the disturbed start needs no model and gives the best fits; it costs 200 of 852 active columns (23 %).
* The slow remainder (−0.24 → −0.10 ADU over columns 200–852) still widens σe by ~4 % (cut vs cut + trend).
* λ is higher on the cut images (ch0 0.145 vs 0.130 e-/pix): later columns wait longer in the serial register, so λ
  depends on which columns are used — whatever is chosen must be the same for every packet.

Recommendation: fix it at acquisition if a test finds the cause; otherwise **cut the first 200 columns** (physical: only
unaffected pixels are used), and treat the residual slow offset as a known ~4 % systematic on σe, the same for every packet
at fixed settings. Subtracting a baseline is not unphysical in itself (the comb shifts rigidly), but the cut does not
depend on modelling it.
